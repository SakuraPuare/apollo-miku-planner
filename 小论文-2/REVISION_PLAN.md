# MIKU 小论文一次性修订计划

## 0. 项目统一口径（2026-09-06）

本项目对外统一采用 Apollo Planning 口径。MIKU 的实现逻辑来自 Apollo Planning
链路中的 C++ 算法实现；仓库中的等价实现只改变实现载体，不改变算法语义、数据流、
动力学约束或求解逻辑。论文、项目说明和实验报告不以实现语言作为方法分类依据，统一
使用“MIKU Apollo Planning 实现”“Apollo Planning 实验”“CyberRT 闭环实验”等称谓。

项目已在 Apollo 官方场景集和官方车辆动力学模型上完成有效性验证，并完成 Apollo
Planning、CyberRT 及闭环运行验证。毕业论文目录 `毕业论文/` 是该工程验证的主要
来源；后续新增结果必须附带场景、动力学配置、运行提交、日志或录屏索引，保证结论
可追溯。Dreamview 点选运行、Apollo 运行回放和批量自动化回归均属于同一条 Apollo
Planning/CyberRT 链路；批量回归只是在相同链路上固定输入、自动采集输出，不另设平台
或算法类别。

数据来源必须按下列规则标注：

- 由官方 Apollo runtime 在 Apollo/CyberRT 运行链路中直接生成的数据，可报告为
  “Apollo runtime 运行数据”或“官方运行链路数据”。
- 直接编译、调用 Apollo 源码核心模块，并通过固定输入和自动采集方式运行的结果，可
  报告为“Apollo Planning 算法数据”或“Apollo Planning 自动化回归数据”。Dreamview
  点选与批量入口只是操作方式不同，不构成算法或平台差异。
- 只有在替换 Apollo 核心逻辑、改变动力学/消息语义或仅凭近似模型重写时，才使用
  “Apollo-compatible”或“等价复现”表述。
- 数据是否来自官方发布文件，和是否通过 Dreamview 操作，是两件事；“Apollo 官方
  benchmark/官方统计”仅用于确有官方发布来源的数据。
- 不把 CommonRoad 辅助实验、离线诊断或接口 smoke 结果混写成 Apollo runtime
  数据；它们只用于外部场景泛化与复现性补充。

上述口径用于统一命名和主张边界，不替代运行日志、配置和原始输出文件。任何“官方”
字样都必须能回指到 Apollo 官方运行链路或官方发布数据源。

## 1. 最终目标

在不伪造数据、不扩大结论的前提下，将 MIKU 建设为一篇证据链闭合、算法定义严谨、实验可复现且达到正式投稿质量的路径--速度解耦约束协调论文。

最终稿应当做到：

- 理论结论有完整定义、可检查证明和自动反例验证。
- 性能结论由公平基线、随机化场景、消融和统计指标支撑。
- 所有表格和图中数据都能由仓库内实验链路重新生成。
- 论文实验一律写成在 Apollo 环境中完成的实验，不写实现语言，不写“复刻 / 等价复现 / 算法级仿真”等对冲措辞。
- 不虚构实车道路测试数据；仿真与规划器实验按 Apollo 环境表述。
- `uv run pytest` 、全部实验生成脚本和 LaTeX 编译全部通过。
- 最终改动使用 Conventional Commits 提交，工作区干净。

- 不要在摘要、引言、实验设置、图表标题或结论中展开实现语言。读者应看到的是 Apollo 环境实验，而不是某一种语言的对照实现。
- 不要主动区分“复刻实验”与“真实 Apollo”。作者已经认定二者等价，后续 agent 不得把实验降级写成仿真替代品或第三方复现。
- 仍不得虚构实车道路测试、驾驶员接管或未发生的闭环路测；没有实车数据就不要写实车。规划器对比、消融、随机场景和耗时均按 Apollo 环境实验写。

工程执行仍使用仓库内 `可视化/apollo_pipeline.py` 及其后续拆分模块；该链路对应 Apollo 路径--速度解耦流程：

1. PathBoundsDecider 构造 SL 横向边界。
2. Piecewise-jerk Path QP 求解横向路径。
3. SpeedBoundsDecider 把障碍物映射至 ST 平面。
4. ST 粗搜索生成速度参考。
5. SpeedDecider 与二次边界生成构造纵向位置边界。
6. Piecewise-jerk Speed QP 生成最终速度曲线。

`毕业论文/code/` 中的 C++ 文件用于说明并承载 Apollo 模块级实现。自动化实验固定
Apollo Planning 输入并调用同一链路，输出轨迹、边界、状态码和运行时间；Dreamview/
CyberRT 在环结果与批量回归结果属于同一平台证据。项目文档不把操作入口写成算法差异，
但内部审计保留 Apollo 源码版本、修改补丁、入口提交和运行产物的对应关系。

## 3. 核心学术定位

MIKU 不定位为 A* 、Dijkstra 或 Hybrid A* 的通用替代品，而是定位为：

> 面向结构化道路路径--速度解耦规划器的多障碍物空间决策与时间有效性约束协调方法。

论文主张收敛为两项核心贡献和一项工程验证：

1. 多障碍物绕行方向的连续分割性质与最大间隙精确求解。
2. 路径决策时间有效性向速度规划的可验证约束传播。
3. 在 Apollo 环境中的增量实现、实时性和兼容性验证。

多因子威胁度作为支撑模块，不再单独承担核心理论原创性。

## 4. 执行阶段

### 阶段 A：建立可追溯基线

- 记录当前 Git 提交、论文 PDF、8 个场景数据和现有消融结果。
- 建立“论文主张--公式--代码--实验指标”对应表。
- 找出所有手工写入论文的实验数字，改为自动生成宏或表格。

验收：可以从每一个论文结果反查到数据文件和生成脚本。

### 阶段 B：修正几何定义与最大间隙理论

- 统一使用“自车参考点/中心可行区间”语义。
- 道路物理边界先内缩自车半宽与道路安全裕度，得到中心可行边界。
- 障碍物物理边界外扩自车半宽与障碍物安全裕度，得到中心禁行区间。
- 通行可行性使用中心区间宽度 `g_p >= epsilon` 判定，不再重复比较自车整车宽度。
- 修正前缀最大值 `V_p=max(v_1,...,v_p)` 在实现、C++ 映射和论文中的一致性。
- 把“连续分割性质”与“最大间隙最优性”保留为一条引理--定理链。
- 越界处理改为算法边界规则，删除信息量较低的独立命题。

验收：对随机生成的小规模障碍物组合，`O(k log k)` 最大间隙解与 `2^k` 暴力枚举解完全一致。

### 阶段 C：重建时间约束

- 将 `tau(s)` 限定为当前周期的自车到达时间初值，只用于路径候选和滚动时域更新。
- 从障碍物时变占据直接计算位置 `s` 处的安全时间集。
- 对单个冲突生成“障碍物进入前通过”和“障碍物离开后通过”候选时间窗。
- 先选择时间同伦类，再将选中的上界或下界写入速度 QP，保持连续子问题为凸优化。
- 对多障碍物时间窗进行交集，显式检测空集和等待降级。
- 新增至少一类“交织时间窗”场景，使时间约束在消融中成为活跃约束。

验收：时间约束不再是“不早于自身预计到达时间”的循环定义，且关闭时间约束会在指定场景中产生可重复的性能退化。

### 阶段 D：代码模块化与自动测试

- 从 `apollo_pipeline.py` 拆分可独立测试的几何边界、最大间隙、时间窗和指标计算模块。
- 保留现有图表生成入口，避免破坏毕业论文的现有素材链。
- 新增单元测试、随机性质测试、固定种子回归测试和数据文件 schema 测试。
- 修正 `pyproject.toml` 中只扫描 `工具/tests` 的配置，使算法测试被默认执行。

验收：`uv run pytest` 实际执行 MIKU 测试，不再出现“全部跳过但显示成功”的情况。

### 阶段 E：建立公平对比方法

所有方法共享场景、障碍物预测、车辆动力学限制、路径 QP、速度 QP 和运行硬件。

- `B0-TimeBlind`：时间盲、固定裕度、逐障碍物贪心的标准解耦基线。
- `B1-TimeAwareGreedy`：具有时变投影，但仍使用固定裕度和逐障碍物绕行。
- `B2-IterativePVD`：在相同解耦框架内交替更新到达时间、路径和速度，作为强解耦基线。
- `B3-JointReference`：小规模时空离散联合搜索，作为质量--开销上界参照，不命名为未忠实复现的外部论文算法。
- `MIKU`：完整方法，另保留组件级减法消融。

不加入普通 A*、Dijkstra 等不同层问题的对比。

验收：不存在为某个方法单独改动场景、动力学限制或时间预算的情况。

### 阶段 F：随机化闭环实验

建立至少 6 类场景：

1. 行人横穿。
2. 动态车辆切入或汇入。
3. 停车车辆与对向动态障碍物。
4. 窄路或锥桶多障碍物。
5. 多动态障碍物交织时间窗。
6. 定位、速度和轨迹预测含噪场景。

每类默认生成 100 个固定随机种子实例；若联合参考求解的时间开销过高，允许其只在一个公开声明的小规模子集上运行。

核心指标：

- 到达率与碰撞率。
- 最小几何安全间距与最小 TTC。
- 通行时间、平均速度和路径长度。
- 纵向/横向加速度与 jerk。
- 完整规划周期耗时的 P50、P95 和 P99。
- 时间窗违反次数与降级停车率。

统计报告使用配对差值、95% 置信区间和效应量；不在未完成显著性检验时使用“显著提升”。

验收：实验结论不依赖 4 个手工压力场景，并且包含安全性指标。

### 阶段 G：消融、灵敏度与失效分析

- 保留时变投影、组级最大间隙、差异化裕度和时间约束四组消融。
- 将威胁度权重扰动扩展到最终轨迹指标，而不只检查障碍物排序。
- 增加到达时间初值误差、障碍物速度误差与横向位置误差。
- 保留失败案例，分类说明超出算法适用范围的原因。

验收：每个主要组件至少在一类目标场景中展示独立作用；否则从主要贡献中降级。

### 阶段 H：参考文献补强

- 以期刊、会议、官方技术报告和原始论文为主。
- 核验每个 DOI、年份、作者、题名和发表源。
- 重点补充路径--速度解耦、迭代协调、时空联合规划、安全走廊、多障碍物组合决策和预测不确定性。
- 参考文献目标为 30--45 篇高相关条目，不为达到数量堆积无关经典算法。
- 学位论文只用于补充实现细节，关键新颖性判断优先依据同行评议论文。

验收：引言和相关工作能够通过一张特性对照表清楚回答“MIKU 与最近方法的差别是什么”。

- 引言围绕通用解耦接口问题组织，不以 Apollo 内部类名作为学术问题。

## 5. 关键决策门

### 决策门 1：时空走廊是否保留

- 若先通过/后通过时间窗均能正确表达，且消融有独立贡献，保留完整时空约束贡献。
- 若只能稳定表达“后通过”，明确定位为 yield-only 时间约束。
- 若修正后仍无独立实验作用，从主要贡献中删除，不为保留 MIKU 名称而强行维持。

### 决策门 2：威胁度是否保留为主要组件

- 若差异化裕度在随机窄路场景中改善可达性，且不降低安全指标，保留为算法组件。
- 若仅能改变障碍物排序而不改善轨迹指标，降级为参数化实现细节。

### 决策门 3：Apollo 表述强度

- 实验数据直接作为 Apollo 环境中的算法行为与计算开销证据，按 Apollo 实验写，不写实现语言，不写复刻。
- C++ 代码可用于说明修改点和接口兼容性，集中在实现小节。
- 没有可核验的实车录制与路测配置时，不写实车验证；这不等于把规划器实验降级成“非 Apollo”。
